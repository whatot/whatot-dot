# 安全化简代码

代码熵是当前没有必要存在、却仍需维护的一组表示、状态、API、分支、包、策略或测试。
产品必须让这些额外内容保持一致，因而承担维护成本。

核心原则：扫描器只产生候选项；真实消费者、归属、历史和验证证据才构成删除依据。
宁可完成少量有证明的删减，也不堆砌猜测。没有找到可安全删除的内容，也是有效结果。

## 选择模式

- 用户要求审计、查找、审查或报告时，只检查并返回排序后的候选项，不修改。
- 用户要求应用、删除、清理、化简或重构时，实施请求范围内最稳妥的删减并验证。
- 删除可达的用户能力、受支持的公开 API、持久化格式或兼容路径属于产品决策。
  除非用户已明确作出决定，否则修改前先说明可观察的取舍。

## 确认契约

1. 阅读仓库说明及作用域最贴近的规范：`AGENTS.md`、`CONTRIBUTING`、架构文档、
   ADR/RFC/决策记录、包清单和测试指南。
2. 检查 `git status`，保留无关工作。分类前先识别生成文件、第三方内嵌代码、迁移、
   测试夹具和对外发布包的路径。
3. 沿入口、配置、注册表、依赖注入、事件、队列、持久化、进程/工作进程和通信协议，追踪真实运行流程。
4. 实施模式下，查明仓库实际使用的局部与广泛验证命令，可行时先执行与变更相称的基线检查。
   基线失败会限制后续检查能证明的范围；记录已有失败，不误报为本次回归。

不能以化简为由删除信任边界校验、授权、安全控制、基本无障碍能力、防数据丢失机制、
持久化数据兼容，或确保资源停止活动的清理逻辑。

审查、新增、修改或删除测试时使用 `test-behavior`，测试选择与执行策略由它负责。
Rust 修改或审查使用 `rust-code`，产品 UI 修改或审查使用 `design-ui`。
本 skill 负责化简的证据流程，不另设语言、测试或 UI 规则。

## 排查不必要的复杂度

从较大或核心的生产代码开始，不只寻找明显未使用的符号。优先使用仓库原生工具：
`rg --files`、`rg`、编译器/静态检查输出、依赖清单和 `git log`。
有帮助时使用已安装的死代码或依赖分析工具，但所有结果都只作为线索。

重点寻找以下候选项：

1. **没有消费者的接口或配置**：没有生产消费者的公开方法、导出、事件、配置键、钩子、包、注册表通知或协议字段。
2. **重复事实**：多个事件、缓存、摘要、状态存储、快照或适配器记录同一事实，需要保持同步。
   工厂或底层重复定义配置默认值，也是策略的副本；默认值应留在所属配置边界，向下传递解析后的值，
   同时保留受支持的独立入口和覆盖语义。
3. **为假设需求预留的通用性**：未设置的调节项、固定的功能开关、未使用的回退逻辑、只有一个实现的接口、
   废弃占位实现，或没有负责方的扩展点。
4. **多余路径或层次**：同一行为有多个入口、只转发的封装、透传包，或让单个调用者更难读懂的辅助函数。
5. **重复生命周期表示**：多个标志、哨兵值、Promise、队列或控制器表示同一个就绪、停止、完成、刷新或释放转换。
6. **防御位置不当**：复制、冻结、校验器、回滚路径或恶意对象测试，保护的是同进程内有类型约束的交接，
   而非真实的信任或所有权边界。查找已失去用途的调试防护、对已知类型必需字段的探测，
   以及把失败转换成空值或默认值成功结果的回退逻辑；区分这些情况与受支持的恢复、可选能力和兼容路径。
7. **手写基础设施**：标准库、原生平台或已安装依赖已经提供的解析器、重试循环、通配匹配、
   消息分帧、差异比较或数据结构。
8. **仅为辅助材料保留的残余**：只有测试或文档在使用的代码、重复预期输出、过期清单，
   或带来运行与发布成本的演示/测试包。
9. **实现废弃后的残余**：实现已消失，但标志、数据模式、文档、测试、兼容分支或决策记录仍在描述它。

不要把必要的独立性误判为重复。独立后端、适配器、表示或生命周期机制，可能有意验证不同契约，
或保护不同的资源持有方。

## 证明或排除候选项

对每个具体符号、行为或工件：

1. 在全仓搜索符号、文件路径、包名、配置键、事件/协议字符串及其他调用语法。
2. 对每个命中分类：
   - **生产用途**：运行时代码、交付配置、真实入口、迁移和运维脚本。
   - **非生产用途**：测试、文档、注释、快照和生成的预期输出。
   - **尚不明确**：示例、测试夹具、插件、反射、注册表、延迟导入、代码生成和外部消费的导出；检查后再分类。
3. 检查调用者和被调用者，不只统计命中数。核对动态加载、字符串分派、路由、插件清单、
   依赖注入容器、序列化、按环境键查找的逻辑，以及外部包契约。
4. 阅读历史和决策记录：这段设计最初解决什么问题，问题是否仍存在，什么新证据足以推翻原有理由。
   对防御分支或异常处理，指出它处理的可达失败，以及删除后会破坏什么。
5. 梳理异步或有状态代码的归属。将每个状态标志、释放器、取消路径、就绪 Promise 和终态结果，
   对应到明确的负责方或状态转换。
6. 说明删除会放弃什么能力或行为，即使结论是“没有可观察变化”。
7. 估算净减少量：移除的代码、专用测试、文档、配置、生成工件、依赖和概念，减去新增的衔接代码与迁移。
8. 指出一个最小检查，使错误化简能够被发现。

出现以下任一情况时，保留候选项或降低其优先级：

- 存在真实生产或外部消费者。
- 无法排除动态可达性或兼容义务。
- 当前有效决策支持这段设计，新证据不足以推翻它。
- 变更实际是功能或 API 决策，不属于清理。
- 只把复杂度转移到别处，没有缩小契约或减少事实来源。
- 新依赖所需的封装与专用测试，和被删除实现的负担相当。
- 候选项收益太小、证据不足，或与请求范围无关。

审计输出使用以下简短证据记录：

```text
[置信度 / 风险] 候选项
证据：生产消费者；动态入口、公开接口与兼容检查；归属与存在理由
删减：具体移除的代码、工件、依赖和概念
取舍：失去的可观察能力或行为
验证：最小且有判别力的检查；预计净减少量
```

## 实施有证据的删减

1. 每次处理一个所有权边界。修复共同的复杂度来源，不逐个调用者打补丁。
2. 端到端删除过期契约：声明、实现、分支、仅服务于已删除行为的测试、导出、配置、文档、示例、
   快照、生成清单和依赖条目。
3. 保留验证存续可观察契约的测试。测试是证据，不是不可修改的规范，也不能仅为减少行数而丢弃。
4. 将重复状态收敛到真正承担契约的表示；不要用同步封装替代两个事实来源。
5. 优先删除，其次使用标准库/原生能力，再考虑已安装依赖。
   只有减少的实现与专用测试负担，大于衔接代码和供应链成本时，才新增依赖。
6. 没有兼容义务时避免兼容垫片；存在兼容义务时，保留路径或设计明确迁移，不静默删除。
7. 保持每批变更可审阅、可逆，不丢弃用户的无关改动。

代码行数净减少是删减的证据，不是目标。安全化简可能需要增加少量测试或迁移；大量删除仍可能是错的。

## 验证结果

每批非简单变更完成后：

1. 再次搜索已删除的符号、字符串、路径和过期文档。
2. 先运行最小且有判别力的测试，再完成仓库要求的相关类型、静态检查、测试、构建、代码生成或冒烟检查。
3. 重新运行产生该候选项的静态分析工具。
4. Git 可用时运行 `git diff --check`，审阅完整差异，检查是否意外扩大范围。
5. 比较公开接口、持久化、通信协议和用户可见边界的行为；只有提出性能结论时才测量性能。

验证失败时，区分候选项实际承担必要职责、实现不完整，还是基线原本失败。
只回退当前批次或补足证明，不削弱有效检查来强行完成删除。

## 报告结果

审计结果按置信度、风险和净维护成本减少量排列最有价值的候选项。
对已排除或尚不确定的高价值候选项，只有缺失证据可以进一步补齐时才列出。

实施后报告：

- 删除了什么契约或重复事实；
- 可测量时，说明减少的文件、行数、依赖和概念；
- 是否改变用户可见能力或兼容行为；
- 实际执行的验证及结果；
- 有意保留的高价值候选项及原因。

不单凭测试通过宣称安全，也不单凭删除量宣称有价值。
